# 実運用の教訓集 — 痛い目を見てから知るのでは遅いこと

当社（株式会社クラウドネイティブ）が同じ仕組みを約6ヶ月本番運用する中で、実際の障害・ヒヤリ・デバッグから得た教訓集。**このレシピの最大の価値はここにある。** Claude Code は実装を生成する際、該当する教訓をすべて反映すること。

実話は「当社の本番で起きたこと」として記す。顧客情報は一切含まない。

---

## A. LLM API まわり

### A-1. モデルの引退は「静かな全滅」として現れる【実話】

当社の本番で、利用していたモデルの提供が終了し、API が 404 を返すようになった。fail-open 設計（分類失敗 → REVIEW）のため**フォームは正常に動き続け、全件が REVIEW に落ちる「サイレント劣化」が発生**。エラーページも出ないため、検知アラーム（A-7）だけが発見手段だった。

- 教訓1: fail-open には必ず検知を対にする（[安全不変条件 5](DESIGN_PRINCIPLES.md)）
- 教訓2: モデル ID はコードの1箇所に集約し、移行を1行の変更にする
- 教訓3: 利用モデルの提供終了予定（deprecation）情報を定期的に確認する

### A-2. 思考（thinking）が有効だと、レスポンスの先頭ブロックはテキストではない

拡張思考を有効にすると `content[0]` が thinking ブロックになるため、`content[0].text` の直参照は壊れる。**text タイプのブロックを探して取り出す**こと。thinking のみでトークン上限に達し text ブロックが存在しないケースも、分類失敗（→REVIEW）として扱う。

### A-3. 思考トークンは出力上限を食い潰す

思考トークンと出力は `max_tokens` を共有する。分類 JSON ごとき（100トークン程度）でも、`max_tokens` を 500 などにしていると思考に食われて**JSON が途中で切断され、パース失敗 → 全件 REVIEW 劣化**につながる。思考有効時は 4096 など十分な余裕を持たせる。

### A-4. LLM 出力の 1 フィールド欠落が、障害の連鎖に化ける【実話】

当社の本番で、分類結果の `reasoning` フィールドが欠落 → 通知メッセージ組み立て関数が `undefined` で TypeError → 処理全体が throw → キューの再試行 → **確認メールの再送とタスクの重複作成**という連鎖が起きた。

- 教訓: LLM の JSON 出力は「全フィールドが欠落・型不正・切断されうる」前提で受ける。label は enum 検証（不正なら分類失敗扱い）、confidence は 0-100 に丸め（範囲外は既定値）、reasoning は欠落時 `''` フォールバック + 長さ上限（500字など。インジェクション緩和も兼ねる）
- 教訓: `as` キャスト（型の主張）でなく実行時の型ガードで検証する

### A-5. SDK のデフォルトタイムアウトは、実行環境の制約を知らない

Anthropic SDK の既定はタイムアウト10分・リトライ2回。Lambda の実行上限（例: 120秒）を大幅に超えるため、API がハングすると**実行環境側のタイムアウトで死に、分類失敗のログが出ず、アラームにも乗らない**。クライアント側のタイムアウトを実行上限より短く明示し、必ず自前の catch を通す（タイムアウトの階層原則）。

### A-6. few-shot 例もプロンプトインジェクションの経路

修正フィードバック経由で取り込む過去の文面はユーザー由来である。**few-shot 例も `<untrusted_user_input>` タグで包む**。タグ外に置いてよいのは人間の修正操作に由来する正解ラベルのみ。

### A-7. few-shot の取得失敗で、分類本体を止めない

few-shot 例の取得（記録先へのアクセス）は付加価値機能にすぎない。短いタイムアウト（3秒）+ キャッシュ + 失敗時は例なしで続行、とし、**付加機能の障害がコア機能（分類）を人質に取らない**構造にする。

## B. サーバーレス実行環境

### B-1. Lambda で「応答後に裏で処理」は動かない（Cloudflare では動く）

AWS Lambda では `void (async () => {...})()` のような fire-and-forget は、**handler の return 後に実行環境が凍結されるため処理が途中で消える**。全処理を await するか、キュー（SQS）に渡して別関数で処理する。速度は `Promise.allSettled` の並列化で稼ぐ。

一方 Cloudflare Workers では `ctx.waitUntil()` が「応答後の処理続行」の公式手段であり、キューなしで即応答+非同期分類を実現できる。**プラットフォームごとに「裏で処理」の正解が違う**ことを知らないと、片方の常識でもう片方を壊す。

### B-2. 同期応答の上限は、ゲートウェイより短く設定する

API Gateway の統合タイムアウトは 29 秒。同期 Lambda をそれより長く（例: 30秒超）設定すると、**ゲートウェイが 504 を返した後に Lambda が処理を完遂**し、クライアントの再送と合わさって重複レコード・重複メールを生む。同期側は 25 秒などゲートウェイより短くする。

### B-3. 外部 SDK のタイムアウトも実行環境と突き合わせる

AI API に限らず、記録先 SDK（Notion 等）の既定タイムアウト（60秒など）が同期応答の上限を超えていないか確認する。B-2 と同型の問題が起きる。

### B-4. 必須設定は起動時に fail-fast で検証する

環境変数・シークレットの欠落は、リクエスト処理中の不可解なエラーではなく、**起動直後の明確なエラーメッセージ**で検知させる。

## C. キュー・リトライ・冪等性（経路C: キュー構成を使う場合）

### C-1. 下流の失敗を throw すると、非冪等な副作用が二重実行される

通知・メール送信などの失敗を throw するとキューが再試行し、**成功済みの処理（確認メール送信等）まで再実行される**。下流サービスは失敗を内部で catch してログのみ残す（never-reject）。その代償として、DLQ にもアラームにも自然には乗らなくなるため、**ログ文字列のメトリクスフィルタ + アラームを必ず併設する**（ペア設計）。

### C-2. キューの可視性タイムアウトは関数タイムアウトの6倍以上

SQS + Lambda イベントソースの推奨値。短いと処理中のメッセージが再配信され重複処理になる。

### C-3. maxReceiveCount は最低 5

一時的なスロットルでも受信カウントは加算される。小さい値だと**正常なメッセージが早期に DLQ 送りになる**。

### C-4. 保持期間: ソースキュー4日 / DLQ 14日

イベントソース停止などの長期障害時、既定の保持期間だと未処理メッセージが DLQ を経由せず期限切れで消失する。DLQ 側も「期限内に対応しないと消える」ことを運用手順に明記する。

### C-5. DLQ の再投入（redrive）は非冪等リスクを伴う

部分成功後の再投入は、確認メール再送・タスク重複・通知重複を再実行する。**再投入前に「どこまで成功していたか」の確認を必須**とし、upsert 型（再実行しても安全）の処理とそうでない処理を区別した手順書を書く。

### C-6. 「最古メッセージの滞留時間」アラームは、失敗し続けるメッセージを見ていない

SQS 標準キューは**3回以上受信されて削除されなかったメッセージをキュー末尾に移動し、`ApproximateAgeOfOldestMessage` の対象から外す**（AWS 公式。redrive policy があっても同じ）。可視性タイムアウト12分なら3回目の受信は滞留24分で、「30分以上滞留したら鳴らす」アラームは**原理的に発火しない**。滞留アラームが検知できるのは「受信カウントが増えないまま止まる」障害（イベントソース停止・権限剥奪）だけである。**失敗し続けるメッセージは関数の `Errors` メトリクスで直接見る**こと。ただし単発の自己回復エラーで鳴らさないための「窓の中で N 回」は、**Period を伸ばすのではなく M-out-of-N（`EvaluationPeriods` / `DatapointsToAlarm`）で書く**。CloudWatch の評価枠は絶対時刻に整列するため、Period を再試行間隔より少し長くしただけでは、エラーが枠をまたぎ続けて**永久に閾値へ届かない**（12分間隔の再試行 × 15分の Period は、位相によって毎回別の枠に入る）。

## D. 通知・修正フィードバック UI

### D-1. 署名検証は body のパースより必ず先

Slack 等のコールバックを受ける場合、`JSON.parse` を署名検証より先にやると、不正 JSON で 500 が返り、**署名を素通りした内部エラーを外部から誘発できる**。順序を回帰テストで固定する（「不正JSON + 不正署名 → 401」「不正JSON + 正署名 → 500」の分岐で順序を証明できる）。

### D-2. ゲートウェイは body を Base64 エンコードすることがある

API Gateway 経由の Webhook は `isBase64Encoded` を確認してデコードしないと、署名検証もパースも壊れる。

### D-3. ボタンに埋めた ID は改ざんできる（IDOR）

修正ボタンの value に埋めたレコード ID を信用して書き込むと、payload 改ざんで他レコードを書き換えられる。**メッセージ ID からの逆引きで実レコードと突合してから書き込む**。署名付きリンク方式の場合は HMAC 署名を必ず検証する。

### D-4. 「AI と同じラベルのボタン」は確認操作として押される【実話】

当社の通知には AI 判定と同じラベルの修正ボタンも常に表示されていたため、運用者が「承認・確認」のつもりで押し、**修正記録に「LEAD→LEAD」のような同一ラベル修正が混入**した。対策: AI 判定と同じラベルのボタンは非表示にするか、「正解」確認ボタンとして別扱いにする（正解の記録は精度測定に使える）。

### D-5. 修正しても AI の元判定を上書きしない

修正操作は「人間判定」「正しいラベル」を**別フィールド**に記録する。AI の元判定を上書きすると、精度の測定（どれをどう間違えたか）が永久にできなくなる。

## E. ボット対策（AI 分類の前段）

### E-1. ボット検知時は成功を装って黙殺する

honeypot（隠しフィールド）への記入や 3 秒未満の送信を検知したら、**エラーではなく通常の成功応答を返して黙って捨てる**。エラーを返すとボットに検知手法を教えることになる。

### E-2. トークン検証はホスト名まで確認する

Turnstile / reCAPTCHA の検証は「トークンが有効か」だけでなく、**どのサイトで発行されたトークンか（hostname）を許可リストと突合**する。他サイトで取得した正規トークンの流用を防ぐ。

### E-3. 全入力フィールドに長さ上限を敷く

会社名100 / 氏名50 / メール254 / 本文1,000〜2,000 文字など。プロンプト肥大（コスト）と攻撃面の両方を抑える。

## F. 観測性

### F-1. ログ文言はアラームとの「契約」である

ログ文字列マッチのアラーム（メトリクスフィルタ）を使う場合、**ログ文言のリファクタでアラームが無音化する**。対策: アラーム定義から検知文字列を抽出し、実際に失敗を起こして実ログ出力と一致することを検証する回帰テストを書く（IaC とアプリログの契約をテストで固定する）。

### F-2. メトリクスフィルタは構造化ログの形式に依存させない

ログが JSON 構造化されていても、フィルタはプレーン文字列でマッチさせる。ログ形式（ランタイムのフォーマット）変更で壊れない。

## G. キー・バリューストア（経路A/B: Workers KV を使う場合）

### G-1. 失敗の「印」を2回目の書き込みで足さない

Workers KV は同一キーへの書き込みを**1秒に1回**に制限し（超過は 429 を throw）、**並行書き込みは last-write-wins で発行順の保証が無い**（いずれも Cloudflare 公式。順序が要るなら Durable Objects）。しかも `put()` は中断できない（`AbortSignal` を取らない）ので、タイムアウトで諦めた書き込みも裏で走り続け、**後から着地して次の書き込みを巻き戻す**。

そのため「1回目で本体を書き、2回目で失敗の印を書き足す」設計は、(a) 順序逆転で印が消える、(b) 間隔を空けたつもりでも「着地」の時刻は測れないので 429 で印だけ落ちる、(c) 印を書く段が処理の尾部にあり実行時間の上限で打ち切られる —— の3経路すべてで**印だけが落ちた記録**を作る。その印が「人間がその記録に到達できる唯一の手段」なら、これはデータの消失と同じである。

対策は**印を書く段を無くし、書き込みを1回に畳む**こと。そのために「通知してから保存する」よう順序を入れ替えてよい（通知の成否まで含めて1回で確定させる）。競合相手が存在しなくなるので3経路とも構造的に消え、コードも短くなる。

やむを得ず同一キーに複数回書く場合（受付時に台帳を作り、分類確定後に更新する等）は、(1) 書き込みの**間隔の起点を「直前の put の完了時刻」にする**（発行時刻を起点にすると、遅い put の後で密着して 429 になる）、(2) **後続の put が唯一の可視化手段にならない**構造にする（先に書いた側だけでも人間が到達できる面が残るようにする）、の2つを満たすこと。

なお「通知してから保存する」に替えると、通知に載せた人間向けリンク（修正リンク等）を人が実行してから最後の put が着地する競合窓が生まれる。通常は put のほうが桁違いに速いので実質起きないが、KV が劣化して put が期限超過（裏では継続）した場合には人の操作が巻き戻る。巻き戻っても記録自体は残り再操作できるので、可視性（不変条件2）と引き換えに受容する判断はありうる —— **受容するなら必ず文書に残すこと**。

### G-2. 索引（metadata）と本文は必ず同時に書く

`list()` の metadata で絞り込み、本文 `get()` で確定する二段構えにすると、metadata と本文が**別々の真実**になる。片方だけを更新すると「get はされるのに一覧に出ない」不可視レコードが生まれ、操作数だけを食う。両者は常に同じ `put()` で書くこと（**表示側だけを駆動するテストでは、この不整合は原理的に検出できない**）。

### G-3. `list()` は「キーが空」でも終端とは限らない

Workers KV は削除済み・期限切れキーを内部で走査するため、**`keys` が空配列なのに `list_complete: false`** を返しうる（公式が明記）。終端判定は必ず `list_complete` で行い、ページングの打ち切り条件を「取得したキーが進んだか」だけに依存させないこと（cursor の前進も独立に数える）。
